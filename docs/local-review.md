## 设计分析

原实现只发送选中原文和当前评论，无法可靠回答依赖附近段落、历史讨论的问题。
Claude Code 现有路线通过 hook 递送信件，信件要求 Claude 读取原笔记理解上下文。
本地 Codex 路线使用 `codex queue` 唤醒已有任务，由插件附带上下文快照并校验写回。

这次补齐以下内容：

1. **原文前后正文**：从与触发评论相同的已保存笔记版本提取；先去掉其他评论线程的评论体，再截取附近正文。
2. **当前评论线程**：附带本次问题之前的评论及回复，包含作者、时间、类型；本次问题单独提供，后面的讨论不会提前混入。
3. **超长内容**：总输入上下文最多 40,000 个 JSON 序列化字符；附加快照最多 18,000，原文前后各约 3,000。长线程优先保留最初问题和最新回复，省略与截断明确标注。
4. **连续追问**：使用当前笔记与线程快照作为依据，不拿目标 Codex 任务中的其他讨论补齐缺失事实。
5. **恢复一致性**：快照随投递记录和请求持久化，重启、失败重试沿用同一份；上下文变化不改变通知去重键。
6. **可审查性**：“Codex 自动回复状态”中展开“发送的上下文”，可查看本次实际附带的数据。
7. **独立启用**：成员窗口与设置页共享同一个 Codex 开关；Claude Code hook 独立显示。

快照模式不足以回答时会说明缺失或追问。后续已新增独立可选的跨笔记查找，见 [跨笔记审查记录](codex-research-review.md)；附件/PDF 仍不在范围内。
模型仍使用所绑定任务的原模型、权限与额度；上下文可能通过用户的 AI 工具发送给其模型服务。

## 本轮稳定性优化与验收

### 已完成的优化

- 每条新评论携带隐藏的稳定 UUID；同文、同问题、不同位置分别投递和写回。旧的未投递评论自动补 ID，已处理的历史通知不会重放。
- 同线程向同成员连续追问时，后一个请求等待前一个完成，并附带其实际回答；等待状态可查看，缺失依赖不会被静默略过。
- 发送前和写回前检查整个 Vault 的 ID 唯一性。复制同一带 ID 评论产生歧义时阻止自动处理。
- Markdown 代码围栏、行内代码、缩进代码、HTML 和 YAML 示例不作为评论投递；评论内部代码和隐藏元数据不会吞掉下一条评论。
- 采纳修改建议保留评论 ID 与回复回执，避免重新投信。
- 桌面端状态文件使用真正的文件系统原子替换；信件采用固定请求路径，中断恢复复用原信。扫描失败显示提示。
- 插件运行期间收到文件改名事件时更新请求目标路径。关闭期间的改名仍可能需要手动恢复。
- 新增“检查 Codex CLI”；状态页以可读段落展示原文、当前问题、此前讨论和等待期间补充的回答。

## 用户审查入口

- 在 Obsidian 打开 `Codex 稳定性验收`，查看相同原文的两处评论和甲组连续追问；`Codex 上下文验收` 可检查附近正文及历史讨论。
- 命令面板搜索“Codex 自动回复状态”，展开最新请求的“发送的上下文”。
- 自己在其他测试笔记中添加 `@Codex` 并勾选“通知对方”，检查回答是否符合期望。

## 限制与恢复

- 保持 Obsidian 打开；仅桌面端，CLI 必须支持 `codex queue`。
- 默认快照只传附近正文；开启跨笔记查找后，Codex 可按需读取当前及关联 Markdown 笔记。读取范围是任务提示词约束，不是新建的文件系统沙箱。
- 开关只自动处理新投递通知，不会把历史信件全部重新发送。
- 待回答期间改动原文或触发评论可能阻止自动写回，回答会保留供检查。
- Windows、Linux、移动端未进行实际运行验证；当前验收环境为 macOS、Obsidian 1.13.7。
- 关闭 Codex 自动回复可暂停发送与写回。已排队任务仍可能完成。
- 当前仅支持一个桌面实例为同一 Vault 自动回复；多设备并发没有分布式锁。
- 复制带隐藏 ID 的整条评论后，应重新创建需要独立回复的评论；插件不会猜测哪个副本是原件。
- 新导入的带通知笔记需要保存一次、手动全库投递或等待下次启动扫描。
- 手机上的普通信箱状态保存仍使用文件接口写入并保留临时副本，不宣称具备桌面端的原子覆盖保证。
- 本轮安装前备份位于本机 Codex backups 目录的 `agent-comments-before-hardening-20260925-224510`；其中包含旧插件、状态和测试笔记初稿。
